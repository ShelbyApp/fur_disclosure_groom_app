# Connect Fur Disclosure to Supabase

**Public landing gallery:** run [007_public_gallery.sql](../supabase/007_public_gallery.sql) after 006 for internal 1–10 photo quality scores, uploader categories and the landing gallery's public read endpoints. No app environment variable changes are needed. See [Public gallery](PUBLIC-GALLERY.md) for behavior and permissions.

**Onboarding and photo sharing (November 19):** run [006_lookbook_sharing.sql](../supabase/006_lookbook_sharing.sql) after the directory deployment. It is safe to rerun, adds Private/Public and an optional directory provider ID to photos, and leaves existing and groom-generated photos private. Owners can change sharing, captions and tags; they cannot change photo ownership. Approved provider names are assigned by the database. `fd_find_photo_providers` is an authenticated, bounded search across all provider types. `fd_public_lookbook` exposes only explicitly public photos, caption, dog name/breed, provider and date; underlying photo/profile/history tables remain owner-only. The public community browsing page and contests are not implemented by this update. Public choices and tags require 006; existing private untagged uploads remain compatible before it is applied.

Signup now stores `fd_account_role` (`owner` or `groomer`) in Auth user metadata and consumes the landing page's role flag. The existing allowed root redirect still works for email confirmation. Existing accounts default to owner and are never reassigned by an incoming URL. This is onboarding context only, not a security role. Both account types save contact details in `fd_owner_profiles`; groomer users open a profile entry with forthcoming tools and may also use the dog-owner features. No additional environment variables are needed.

**Directory update:** after owner migrations 001 and 002, run [the combined directory SQL](../supabase/deploy/RUN_THIS_create_tables_and_import.sql). It creates/updates the directory tables, applies [005 storage safeguards](../supabase/005_directory_storage_policy.sql), and imports the 41 providers in one transaction. It is safe to rerun and upgrades the earlier 003/004 pilot. Use this combined file instead of the original seed. See [Directory](DIRECTORY.md) for source and moderation details. The user confirmed the initial import returned 25 Sarasota, 8 St. Petersburg and 11 Tampa results on November 18, 2026.

Use project `zdpheikochvtjirgskuv`. The planner’s API endpoint is already set to `https://zdpheikochvtjirgskuv.supabase.co`. The dashboard URL is for administration.

**Updating an existing installation:** run [002_profiles_groomers_lookbook.sql](../supabase/002_profiles_groomers_lookbook.sql) once in the SQL Editor before deploying this version. Do not rerun 001. This adds city/state, private saved groomers and private dog photo collections. It backfills current-coat photos from prior grooms and adds a trigger to collect them from future completed grooms. The trigger touches only Fur Disclosure tables. Existing environment variables and auth settings stay valid. New installations run 001 below, then 002.

1. Open the [SQL Editor](https://supabase.com/dashboard/project/zdpheikochvtjirgskuv/sql/new). Paste and run the full [migration](../supabase/001_owner_profiles.sql) once. It creates three new tables in one transaction. A name collision stops the transaction for inspection. There is no trigger on the shared users table.
2. Open [Settings → API Keys](https://supabase.com/dashboard/project/zdpheikochvtjirgskuv/settings/api-keys). Copy a **publishable** key beginning with `sb_publishable_`. This build accepts only that key type. Keep database passwords, secret keys and service-role credentials out of the website and GitHub.
3. In the **planner’s Vercel project**, open Settings → Environment Variables. Set **SUPABASE_PUBLISHABLE_KEY** to the copied key for Production and any preview deployments that should use this project. Redeploy. Vercel runs `npm run build` and serves `dist/`. The frontend is expected to contain the publishable key. Owner access is enforced by login and database row policies.
4. In [Authentication → URL Configuration](https://supabase.com/dashboard/project/zdpheikochvtjirgskuv/auth/url-configuration), **add** the exact deployed planner root, `https://groom.furdisclosure.com/`. For local testing, add `http://127.0.0.1:4381/`. Keep the existing project's Site URL and other redirects. Ensure Email sign-in and new signups are enabled for the intended audience. The planner uses email and password for login. Supabase handles signup confirmation according to the project settings and sends password recovery emails. Confirm the shared project's email provider can deliver to your test recipients; project templates or SMTP changes affect the other app as well.
5. Choose Create an account, enter an email and password, and confirm the email if prompted. Save an owner name, add two dogs and give each different defaults. Finish a groom, open its history entry, copy it, and change one spot or haircut detail. Both entries should remain in the selected dog’s history. Sign out and log back in with email and password to check the saved profile and both visits. To test an existing email-link account, use Forgot password with its original email, open the reset link, set a password and log in again.

**Local setup.** Install Node 22.14+ and run `npm ci`. Copy `.env.example` to `.env.local`, set the same publishable key, then run `npm run dev`. The local file is ignored by Git. Guest entry is hidden; login requires the publishable key.

**Health and contact update:** no new migration is needed after 002. Health and comfort defaults use the existing `fd_dogs.care_defaults` JSON. The selected groomer ID and visit-only secondary contact use the completed groom’s existing JSON snapshot. Both primary and secondary contacts are omitted unless the owner chooses to include contact details.

**Shared project behavior.** Supabase Auth uses the project's existing pool of identities. A Fur Disclosure profile is created when the owner saves their details. Only the Fur Disclosure tables are written by this app. Each row belongs to the signed-in owner. Composite keys keep dog history and copied visits within the same owner and dog. Clients can insert and read their completed plans. Changes to an earlier groom are saved as a new record.

**What is stored.** `fd_owner_profiles` contains the owner's display name and optional phone, city and state. The account email comes from the authenticated Supabase session. `fd_dogs` contains identity, birthday and a JSON object of usual preferences. `fd_groomers` stores the individual groomer and business separately, with address, email and phone. `fd_grooms` contains service, optional visit date, copy source and a dated JSON snapshot. For this iteration, the snapshot includes resized photo data and coordinates so a historic plan can be reproduced. `fd_dog_photos` stores resized JPEG/PNG/WebP data with optional captions, related dog and original groom when applicable. Unique per-dog photo hashes avoid duplicates from copied grooms. Inspiration photos remain only in the groom snapshot. The dog profile fetches three recent history labels and 12 photos initially; full history is paginated and full snapshots load only when opened. Profiles, groomers, lookbook photos and completed grooms sync across devices. In-progress drafts belong to one account, dog and browser tab and clear on sign-out.
